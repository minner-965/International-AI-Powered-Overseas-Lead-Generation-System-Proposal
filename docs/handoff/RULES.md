# 规则 / Rules — SIM外贸获客系统

本地用 Claude Code 时可把本文件复制为 `CLAUDE.md`；用 Codex 时复制为 `AGENTS.md`（仓库已有 `AGENTS.md`，内容更全但夹带大量历史阶段记录，本文件是精简、长期有效的版本）。

## 0. 产品与命名

- 产品名 **SIM外贸获客系统**（英文 SIM Overseas Prospecting）；对外邮件落款公司名 **SIM International**。
- 代码、数据库对象、迁移名、`DPV_*` 环境变量、模板键（如 `DPV_FIRST_TOUCH_V1`）里残留的 `DPV` 为历史兼容，保留不改，但**绝不显示给用户**。

## 1. 复用优先（最重要，所有工作都适用）

- 不要重复造轮子。实现任何能力（功能、数据集、集成、UI 组件、脚本）前，先找成熟开源项目、官方 SDK 或公开数据源（类目分类、国家/语言/时区数据、认证、图表、CRM 视图等），许可证、部署、隐私、成本、维护活跃度合适就用它。
- 每次评估先记到 `docs/REUSE_CANDIDATE_REGISTRY.md`（官方来源、许可证、维护状态、用或不用的原因），再加依赖或写替代实现。只写"集成"和"确实缺的那部分"。
- 已在用的复用件：SearXNG（本地搜索）、express-session + connect-pg-simple + @node-rs/argon2（登录）、Node 内置 AES-256-GCM（邮箱密码加密）、Shopify 商品分类（类目与多语言译名）、Node 内置国家名、cloudflared（对外访问）、纯 CSS `data-tip` 提示。

## 2. 安全红线（不可触碰）

- 密钥、密码、API Key 绝不进 Git。只放本机 `.env*`（已在 `.gitignore`）。
- 测试**零真实外部调用**：SMTP / IMAP / Hunter / Exa / Tavily / Feishu / LLM 全部 mock。
- 绝不改写已应用的迁移；要改 schema 就加新迁移（当前最新 066，下一个 067…）。
- 绝不删除业务/审计/线索/外联/抑制/活动/任务历史，也不因为"规则退役""当前计数为零"就删表或删血缘。
- 鉴权、额度、数据隔离、发信资格一律在**服务端**判定，前端只是展示；安全不依赖前端代码保密（前端 JS 任何人都能下载阅读）。

## 3. 商业模式（决定产品形态）

- Simon 是唯一管理员，运营一套托管系统。给中小外贸公司开**商家账号**，默认试用 7 天（可调），之后转为 付费 / 到期 / 停用，全部在管理员账号里设置。商家可推荐朋友，由 Simon 开账号（**不开放自助注册、暂不做在线支付**）。
- 一套系统一个数据库服务所有商家；每条线索、任务、回复、邮件都属于某个商家，商家之间互不可见。搜索用 Simon 的资源（本地 SearXNG 优先，付费接口兜底），受每个商家的月额度和 Simon 的全局上限双重限制。
- 商家在工作台绑定自己的发信邮箱，用自己的公司名发开发信，回复回到自己账号。
- 每个页面都从商家视角设计：按钮明显、首次登录引导清单、每个按钮有悬停/聚焦说明、每页有意见反馈按钮。

## 4. 双语排版

- 对外文案用 `.bi` 结构：中文为主标签；英文同义、小一号、常规字重、浅灰。导航/表头/表单标签英文在中文**下方**；卡片标题/按钮/标签页/药丸英文**紧跟**其后。
- 中英文都用专业、对等的措辞；不改写源证据或返回的业务数据。

## 5. 手机布局（≤900px）

- 按主流移动工作台 / 移动 CRM：底部固定标签栏、暴露每个功能的工作台宫格、贴边列表行、分段式详情页、底部固定操作栏。
- 每个功能按钮都要可见、带文字标签、触控目标 ≥44px；不要把功能藏进汉堡菜单或"更多"。
- 前端改动要在桌面和手机宽度（1440 / 390）真机截图验证，含键盘聚焦、加载、空、错误、长内容、reduced-motion 状态。

## 6. 禁止的对外用词

- 不显示实现叙述或 AI 口吻：`Demo`、`真实数据`、`抓取/采集/爬取/去重`、`规则评分`、`外联已禁用 / Outreach disabled`、以及数据库/Docker/PostgreSQL/爬虫/存储机制的解释。
- 技术词只能出现在开发文档、日志、源码标识符、内部管理界面。
- 批准替换词：`更新客户名录 / Update Company Directory`、`数据更新 / Data updated`、`客户评估与跟进 / Prospect Review & Follow-up`、`商品类目评分 / Product Category Score` 等。

## 7. 任务执行方式

- 非简单任务先用计划模式（多步、含糊、高风险、架构、迁移、部署、跨切面）；清晰原子低风险的小改可直接做。
- 默认拆成可并行、互不重叠文件的子任务，早点起子代理并行（前端/后端/数据库/测试/文档）。主代理负责协调、集成、冲突解决和最终验证。

## 8. Git 工作流

- 开发分支：`claude/gifted-hypatia-59rtaf`。只推这个分支；**没有明确要求不要开 PR**。
- 每完成一项就提交（会话可能中途重启）；提交信息清楚。
- 有个 CI 检查要求：改了非文档代码后，`docs/CURRENT_PROJECT_STATUS.md` 要在最新一次非文档提交之后更新（追加一行即可），否则 `current-project-status` 测试失败。
- 提交信息结尾加（本地自己开发时可按自己的署名习惯）：
  ```

  ```

- 改 `public/`、前端模板、工作台 CSS、用户可见标签或交互前，先读 `.agents/skills/dpv-workspace-ui/SKILL.md` 和 `docs/UI_SYSTEM_V3.md`。
- 视觉基准是 V4 设计稿 `docs/ui/mockup-v4/`（sq-system 风格：220px 深色侧栏、白色顶栏、`#F3F5F8` 画布、主色 `#2563EB`、单一本地样式表、无 Tabler）。
- 不把设计稿里的样例公司、假指标、营销文案、远程 CDN/字体/头像、渐变/辉光等带进生产。
