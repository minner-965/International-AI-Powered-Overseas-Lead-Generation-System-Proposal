# SIM外贸获客系统 · 评分与流程优化方案（2026-10-26）

依据三份评审：评分规则与代码审计、全流程卡点审计（都在本机代码和数据库上只读完成），以及同类成熟产品调研（Apollo、Clay、HubSpot、Hunter、lemlist、Instantly、Smartlead、Woodpecker、ImportYeti、UN Comtrade 等，来源链接见文末）。
所有修改都遵守 `docs/handoff/RULES.md`：鉴权、额度、发信资格一律在服务端判定；历史只追加不删；不改已应用的迁移，新表和新约束从 **068** 开始；测试全部 mock 外部服务。

## 〇、先说一个必须马上处理的问题（已止损）

**总开关关着，"联系人研究"照样在花钱。**
- 原因：联系人研究的开关在代码里写死为"开"（`automation/Phase13AutomationFacade.js:32`），服务端每 30 秒自动触发一次（`server.js:2737`、`:2614`）。它和类目证据服务直接调用 Tavily（`enrichment/EnrichmentService.js:131`、`categoryEvidence/CategoryEvidenceService.js:45`），不经过 SearXNG、不经过花费上限、也不看总开关。Hunter 的单次/每日/每月上限默认都是 20000（`server.js:186-188`），等于没有上限。
- 实际花费：自 10-24 13:00 换回旧库以来，Tavily 共 292 次调用、231 点（约 1.85 美元）；Hunter 26 次调用（用的是已失效的旧密钥）。之前我报的"57 点"只算了 26 日那一小段，**少算了**，以此为准。
- 已做：研究后台两个进程（category-worker、data-worker）已停掉，现在没有任何调用。修复第 1 批后再启动。

## 一、第 1 批：止血与开关（P0，先做）

| 编号 | 改什么 | 为什么 |
|---|---|---|
| A1 | **拆开总开关**：研究搜索、自动首封、联系人研究三个独立开关（新接口 `PUT /api/automation/control/:subsystem`，旧接口保留为"全开/全关"）。联系人研究开关存进 `automation_controls`（068 插入一行 `CONTACT_RESEARCH_EXECUTION`，默认关），不再写死。人工批准过的跟进邮件不再被"自动首封"开关挡住。 | 现在想让商家找客户，就得同时打开全站自动发信；关开关止损又会卡住人工跟进。 |
| A2 | **"只用免费搜索"真正生效**：模式为 `FREE_ONLY / NO_NEW_PAID_SPEND` 时，路由器把单价大于 0 的提供方视为不可用，任务进入"等待免费搜索"暂停态，可恢复；空结果是否转付费另设开关，默认不转。联系人研究和类目证据改为走同一条搜索路由和 `canSpend` 预算检查。Hunter 默认上限降到合理值（每次运行 5、每天 50、每月按套餐）。系统设置里这个模式改成可选项，显示真实值。 | 现在写着"不新增付费"，实际在付费。 |
| A3 | **防止重复发首封**：SIM 自己的首封候选排除已分配给商家的企业；按收件人做跨发信方的冷却期（30 天内任何一方发过就拦），避免同一买家先后收到 SIM、商家 A、商家 B（可能是竞争对手）的首封。 | 现在按发信方分开算，会重复打扰买家。 |
| A4 | **商家自动首封默认关**：068 加 `merchants.auto_first_touch_enabled`（默认 false），商家在"绑定发信邮箱"页确认开启；试用期默认走"人工确认后发送"。 | 现在邮箱一验证、全局一开，就自动从商家邮箱发信；同类产品（Apollo 等）试用期默认首封人工确认。 |
| A5 | **商家邮箱故障隔离**：某个商家邮箱卡住只暂停这个商家，不再关闭全站自动首封；"测试连接"偶发失败只记录结果，连续失败 3 次才停用，不再立刻清空"已验证"。 | 现在一个商家的 SMTP 卡 10 分钟会让全站停发；一次网络抖动会静默停掉商家的发信和收信。 |
| A6 | **计数和收信修正**：SIM 跟进的每日上限只算 SIM 自己发的；试用到期的商家，已发邮件的回复继续同步进来（只读）。 | 现在商家发信会挤占 SIM 的额度；到期后回复丢失。 |

## 二、第 2 批：流程卡点（P0/P1）

| 编号 | 改什么 | 为什么 |
|---|---|---|
| B1 | **手动添加企业和联系人**（管理员）：新接口和页面，录入后标记来源为"手动"；可勾选"测试企业"（068 新表 `company_test_flags`，只追加）。手动企业**不进自动首封**，走"草稿 → 人工批准 → 发送"；测试企业的收件人必须在 `.env` 的 `TEST_RECIPIENT_ALLOWLIST` 白名单里（服务端判定）。 | 现在企业只能由研究产生，没法验收、也没法录入展会/老客户介绍的线索；同类产品都支持手动添加和导入。 |
| B2 | **首封测试发信**：管理员或商家可以随时用真实首封模板（可选一家真实企业的变量）发一封带 `[TEST]` 的测试信到自己的邮箱或白名单地址；不受市场发信时段限制，不占额度、不写首封记录、不影响"是否已联系"。每次发送追加记录（068 新表 `first_touch_test_sends`），每天限 10 次。 | 现在只能等迪拜工作时间、还要有一家完整评估过的企业才能看到真实首封效果；lemlist/Instantly/Smartlead 都有"发测试信给自己"。 |
| B3 | **取消研究任务**：任务和批次上加"取消"按钮和接口，状态记为已取消，保留全部记录和花费账单。 | 刚才只能直接改数据库。 |
| B4 | **商家业务范围在服务端生效**：商家建研究任务只能选自己范围内的类目和市场（范围外返回 422）；新建任务默认带上商家自己选的类目；商家首封里写的类目只取商家范围内的。 | 现在商家能搜范围外类目，首封可能以商家名义写别的类目。 |
| B5 | **界面问题**：研究任务列表连衣裙显示成"其他类目"（服务端返回类目中文名）；绑定邮箱"测试连接"后右侧状态不刷新（成功、失败都重新读取）；商家"同步到飞书"开关目前无效，先标成"暂不可用"。 | 验收中发现。 |
| B6 | **研究复用不串数据**：研究任务跨商家复用时，商家 B 只能看到分配给自己的企业，并按次扣 B 的额度。 | 现在 B 复用 A 的任务能拿到 A 的全部企业，且不扣额度。 |

## 三、第 3 批：评分规则（P0/P1）

| 编号 | 改什么 | 为什么 |
|---|---|---|
| C1 | **零售连锁、百货能进池**：企业核验加入"零售连锁/百货"类型（068 扩展证据类型约束），有多门店或门店网络证据 + 类目证据即可核验通过；"仅面向消费者"的拦截不再挡 B2B 零售连锁；去掉美妆项目遗留的 salons、pharmacies 词。 | 目标买家里写了百货和连锁零售，但核验规则根本没有"零售商"这一类，这批买家整体进不了池。 |
| C2 | **"泛相关"必须有类目证据**：至少一条已批准类目（或父类目）观测，或明确的综合百货描述；只有泛泛经营信号的降为"待研究"。规则版本升到 `v2_MC08`，决策表照旧只追加。 | 现在一家已核验的电子产品批发商，只要页面有 "locations" 就能进池。 |
| C3 | **收件人逐条评估**：最优地址被抑制或退信时，自动用同公司下一个有效地址；硬退信只封这个地址，不再封整家公司；决策人邮箱必须和公司域名一致，才算"域名已核验"。 | 现在既有误排除（一个地址出问题整家封），也有误放行（Hunter 找到的任意邮箱被当成官方邮箱）。 |
| C4 | **修公司分的 bug**：产品词加词边界（现在 "address""laptop" 都会命中 dress/top，几乎人人拿满 20 分）；Hunter 返回的大写 `VALID` 能正确得分；没有数据的维度不计入分母；规模分改为中型企业最高、超大企业降权（更适合小出口商）。新版本号重算，旧分数保留。 | 当前分数失真，而它还用于排序。 |
| C5 | **自动首封选人不再"饿死"**：候选 SQL 先排除没有有效收件人、已抑制、已联系过的企业，再按优先级取；池内按"档位 → 买家模式 → 规模 → 进口证据 → 联系就绪度"排序，不再按公司名。 | 现在每轮只看前 50 家，前面 50 家没邮箱时，后面合格的永远轮不到。 |
| C6 | **类目采购分口径统一**：按已覆盖维度归一（和商业契合分一致），类目证据不再同时贡献三项分数；前后端用同一套档位阈值。 | 现在一组证据重复计分；缺证据当 0 分；前端筛选和后端档位是两套定义。 |
| C7 | **邮箱核验更贴近实际**：核验有效期统一成一个设置，默认 90 天、发信前过期自动复核；catch-all 地址 Hunter 分数 ≥85 可自动发，80–85 转人工确认，<80 和 unknown 不发；Gmail/Hotmail 这类个人邮箱，只要在对方官网公开过就允许。 | 现在 3 处写着 3 个不同有效期，会卡住线索；catch-all 一律不发，而企业邮箱里 catch-all 很常见；墨西哥、巴西、阿联酋小买家大量用 Gmail。阈值参考 Hunter 官方建议。 |
| C8 | **更多市场的检索和证据词**：补齐巴西、澳大利亚、加拿大、新加坡的市场档案；类目证据词用 Shopify 官方多语言译名生成，覆盖西语、葡语、阿语；单独的 "locations""shop online""inventario" 不再算证据，必须带数量或上下文。 | 巴西葡语网站现在拿不到证据；宽泛词几乎每个网站导航栏都能命中。 |

## 四、第 4 批：发信合规与送达率（P1，参考 Google/Yahoo 2024 规则和同类产品）

| 编号 | 改什么 |
|---|---|
| D1 | 每封开发信加 RFC 8058 一键退订头（`List-Unsubscribe` + `List-Unsubscribe-Post`），正文保留可见退订链接。 |
| D2 | 商家绑定邮箱时自动检查发信域名的 SPF、DKIM、DMARC，结果显示在页面上，缺失时给出配置指引（先提示，不强制拦截）。 |
| D3 | 退信熔断：单个邮箱近 100 封退信率超过 3% 或出现投诉，自动暂停该邮箱，人工恢复。 |
| D4 | 新邮箱逐步放量：第一周每天不超过 10 封，之后每天加 1 封，上限按商家额度；两封之间至少间隔 15 分钟。 |

### Simon 的决定（2026-10-26）

1. 零售连锁先用 C 模板。
2. 不单独起草西语/葡语模板，改为**加翻译功能**：发信时能看到的写信框和模板编辑框里，可以把中文或英文内容直接翻译成目标语言（西语、葡语、阿语等），也能直接改写；优先安装开源翻译服务（候选：LibreTranslate，可本机 Docker 部署），评估记入 `docs/REUSE_CANDIDATE_REGISTRY.md`。列入第 2 批（B7）。
3. 收紧"泛相关"前，先用现有 138 家做新旧对比给 Simon 看。
4. 试用商家首封默认人工确认：开。

### Simon 追加的要求（2026-10-26）

- **B8 开关全部上界面**：所有开关（研究搜索、自动首封、联系人研究、只用免费搜索、商家自动发信、各功能开关等）都要在界面上能看到、能直接点，管理员和商家各自看到自己能操作的那部分，并写清楚每个开关管什么。
- **B9 API 密钥配置页**：管理员在界面里配置系统用的各类密钥（搜索、邮箱核验、飞书、翻译、模型等）；商家也能填自己的密钥，填了就用商家自己的、花商家自己的额度。密钥只存在服务端并加密保存，页面只显示"已配置 / 末四位"，不回显明文。
- **C3/C7 补充（Simon 2026-10-26）**：搜到的企业只要有可用的商务邮箱就可以发开发信，不要求邮箱属于具体负责人。企业官网公开的邮箱、或与企业域名一致的邮箱（info@、sales@、buying@ 等），核验通过即可进入首封；仍保留退订、退信、抑制和核验检查。
- **E1 澄清（Simon 2026-10-26）**：低成本模型只在系统内部做执行工作，例如对搜索到的企业按执行规则文件做比对、筛选、评分；先出评估结论。
- **E1 评估辅助执行的低成本模型**：评估搜索评分和其他模块要不要加一个低成本大模型辅助执行。如果加，模型只负责执行明确的子任务（例如从网页里提取结构化信息、翻译、回复分类），判定和放行仍由服务端规则决定；同时写一份给模型的执行标准 `docs/llm/LOW_COST_MODEL_EXECUTION_STANDARD.md`，模型的密钥也放进 B9 的配置页。

## 七、执行方式

- 按批次顺序执行，每批内部按"互不重叠的文件"拆成多个子任务并行开发：服务端开关与花费、首封与收件人、商家与界面、评分规则、迁移 068、测试各一路。
- 迁移 068 由一个子任务统一编写（新增 `CONTACT_RESEARCH_EXECUTION` 控制行、`merchants.auto_first_touch_enabled`、`company_test_flags`、`first_touch_test_sends`、证据类型扩展），先在隔离数据库回放，再在本机执行。
- 每批完成后：全量测试、需真实数据库的测试、浏览器在 1440 和 390 宽度下逐页检查、更新 `docs/CURRENT_PROJECT_STATUS.md`、提交推送、等 GitHub 测试通过。
